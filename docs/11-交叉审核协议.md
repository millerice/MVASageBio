# 11 — 交叉审核协议：外部大模型对抗审查（2026-09-15）

> **定位**：与我方 M5 子代理对抗门**互补而非替代**——M5 的 claim 溯源审计是代码强制的
> （报告引用 ↔ 台账 EV 逐条核对）；外部交叉审核的独有价值 = **血统独立性**（脱离
> Claude 训练分布的盲区）+ **联网核源**（逐条打开 tier-0/1 原始来源比对转述，这是
> 任何纯记忆模型包括我自己都做不到的——台账出自本方之手，自审忠实度结构上无效）。
>
> **协议 > 选型**：任何旗舰模型配一句「帮我审一下」只会得到奉承。价值在下面的
> 结构化协议本身。

## 0. 合规约束（每轮均适用）

- **只送公开级材料**（见 §1 白名单）；私有台账、私有笔记、`data/**` 一律不送
- 服务需为 **Processor 型**（不训练、不取得数据权利、限时留存）；消费级免费档
  条款存疑时，白名单材料本身即 CC-BY 待公开物，风险兜底为「公开前已在公开渠道可见」
  ——但记录义务不免除
- 每轮交互后登记 `docs/llm-usage.log`（行模板见 §6）
- 发现与处置全部落在 `docs/cross-review-findings-2026-09.md`，不散落对话

## 2. 五轮总览

| 轮 | 角色 | 联网 | 核心问题 | 输入 |
|---|---|---|---|---|
| R1 | 引文核查员 | **必须** | 43 条被引 EV 的转述是否忠实于来源；报告复述是否超出台账 | 报告+台账+docs/10 |
| R2 | 领域科学家 | 可选 | 机制链与四个候选假说的科学软肋 | 报告+机制链 |
| R3 | 合规官 | 否 | 官方规则/表单 11 问逐条对照 | 报告+rules.py+evaluation.py |
| R4 | 医学安全编辑 | 否 | 猎杀一切可读成治疗建议的句子（出局红线） | 仅报告 |
| R5 | 红队评委 | 否 | 按官方 Rubric 严打分 + 强制 top-5 缺陷 | 仅报告 |

**操作纪律**：
- 每轮**开新会话**（避免角色串味与上轮发现的锚定污染）
- R1 最慢（联网逐条），先启动；R4 最快，可先行拿到红线结论
- 若接入两家模型（如 Gemini + GPT）：同协议各跑一遍，**取交集 = 高置信必改**；
  单侧发现降级为人工判断
- 所有 prompt 为英文（与被审对象同语言），要求审查者**用中文输出发现**

**全局反奉承前缀**（贴在每个 prompt 开头）：

```text
GLOBAL RULES
- You are an independent external reviewer. The team that wrote these artifacts is not your audience and cannot be offended.
- Do not open or close with praise or summary. Output findings only, in the specified format.
- If a category has no findings, write "无发现" for it — do not invent findings to fill space.
- Severity order: fact errors (wrong number/direction/source) > overstatements (claim stronger than its source) > presentation issues.
- Write findings in 中文; keep quotes verbatim in the original language.
```

## 3. 五轮 prompt（英文原稿，整块复制即用）

### R1 — 引文核验（联网）

```text
ROUND R1 — CITATION VERIFICATION (web-grounded)

ROLE
You are an independent citation auditor. Your only job is to verify that claims match
their cited sources. Do not evaluate the science, the strategy, or the writing.

INPUTS (attached)
1. report.md — a hackathon drug-repurposing report. It cites evidence entries inline
   as [EV-xxxx].
2. evidence.jsonl — the evidence ledger. One JSON object per line; relevant fields:
   id, claim, claim_type, tier (0 = official page/source code, 1 = peer-reviewed),
   source (title/url/publisher), evidence (what was actually seen), counter_evidence,
   confidence. Entries are in Chinese; most sources are in English.
3. plan.md — the pre-registered data-analysis plan (context for EV-0084/0085/0087).

NOTE ON MISSING IDS
The report cites EV-0077 and EV-0086. These live in a private appendix
(variant-/karyotype-level detail excluded by the dataset's genomic-data rules) and are
intentionally not in the attached ledger. Do not flag them as missing.

TASK — three-point audit, in this priority order:
A. Ledger vs source (web): for each EV entry the report cites (43 ids), open the cited
   source (or an authoritative equivalent) and verify: numbers, direction of effect,
   sample sizes, CIs, approval status, quoted terms. Verdict per entry:
   CONFIRMED | OVERSTATED (claim stronger than source — state exactly what the source
   does support) | REFUTED (contradicted — quote the source) | UNVERIFIABLE (state why:
   paywall, gone, non-indexed)
B. Report vs ledger: for each report citation, check the report's paraphrase does not
   exceed its EV entry.
C. Time-sensitive negative claims (highest priority): the report asserts no
   interventional trial for MVA/BUB1B has ever been registered (EV-0059) and no
   pharmacological SAC enhancer exists (EV-0068). Re-query these live
   (ClinicalTrials.gov; PubMed) and date-stamp your result.

OUTPUT (中文; quotes verbatim in original language)
1. Per-EV verdict table: EV id | verdict | one-line discrepancy (if any) | source URL + access date
2. All REFUTED/OVERSTATED items, most severe first, each with the exact source quote
3. Report-vs-ledger overstatements, if any
4. Fresh re-verification result for item C, with query date
Budget discipline: if an entry cannot be verified within reasonable effort, mark
UNVERIFIABLE and move on — never guess.
```

### R2 — 机制与药理对抗审查

```text
ROUND R2 — MECHANISM & PHARMACOLOGY ADVERSARIAL REVIEW

ROLE
You are a senior scientist in chromosome segregation / spindle-checkpoint biology and
translational pharmacology, reviewing for a top journal. You enjoy finding the flaw.
You are not a copy editor.

INPUTS (attached)
1. report.md — the report.
2. mechanism_chain.json — the machine-readable causal chain: 14 nodes (N1–N13), edges,
   every node claim graded fact / inference / hypothesis with ledger ids.

NOTE ON MISSING IDS
EV-0077 and EV-0086 are in a private appendix (genomic-data rules) and intentionally
absent from any attached file. Do not flag them as missing.

TASK
Attack the causal chain and the four drug hypotheses node by node. For each node: is
the evidence class adequate for how the node is used? Where does inference get silently
upgraded to fact? Where is a correlation asked to carry causal weight?

The team names its own soft spots — cover these, but do not limit yourself to them:
1. N3: allele 2 (kinase-domain missense) → "protein-destabilizing hypomorph" is inferred
   from the allele class via transfection studies, not assayed in patient cells; a
   minority view attributes disease to residual kinase activity. Is the report's framing
   of this as inference honest and adequate?
2. N5: the ≈13% / ≈6% BUBR1-expression thresholds come from cell and mouse systems. Is
   transferring them to a human compound-heterozygote defensible?
3. §2.2: metformin (support aneuploid-tissue fitness) and chloroquine (selectively
   impair aneuploid cells) pull in opposite directions. The report separates them by
   "clinical scenario" (development-support vs cancer-prevention). Is that a real
   biological distinction or a rhetorical device?
4. The C. elegans platform: SAN-1/MAD3 lacks a kinase domain. Do the worm predictions
   (§3) actually test what the report claims they test?
5. Niacinamide's evidence base is BubR1-insufficient aging mice, not MVA mutants — does
   the report carry this gap everywhere it makes the L1 argument?

OUTPUT (中文)
For each attack: target (node id / report section) | the attack, phrased as a skeptical
reviewer would | severity 高/中/低 | what evidence would resolve it.
End with: THE SINGLE WEAKEST LINK in the chain, one paragraph.
```

### R3 — 规则合规审计

```text
ROUND R3 — RULES & COMPLIANCE AUDIT

ROLE
You are the hackathon compliance officer. You have the official rules in hand. Be
mechanical, literal, unsympathetic. A requirement is met only if a strict reader can
find it, in the right place, without generosity.

INPUTS (attached)
1. rules.py — source code of the official Rules page (the authoritative text is
   embedded in this file as string literals).
2. evaluation.py — official evaluation logic (context for what each track must contain).
3. report.md — the submission report under audit.

CONTEXT
The official methods-description form (xlsx; A-column questions A1–A17) is answered
inside report §4 (labels A7–A17 quoted there). Track-2 required deliverables at
submission time: report including variant-mechanism characterization, GitHub URL,
3-minute video link.

TASK — checklist audit, rule by rule:
1. For each methods-form question A7–A17: is it answered in the report? Flag any a
   strict reader could call unanswered or evasive.
2. Track-2 hard requirements: (a) every nominated drug market-approved — scan the drug
   table and alternates for any not verifiably approved; (b) variant-mechanism
   characterization present (§1); (c) generative-AI disclosure present and specific.
3. Release obligations visible in the report: CC-BY statement, official acknowledgment
   text, dataset-citation placeholder.
4. Anything in the report that conflicts with rules.py (prohibited content, data-use
   statements, deadline obligations).

OUTPUT (中文)
Table: 要求 | 出处（rules.py 行号 / 表单问题号） | 报告位置 | pass / fail / unclear | 备注.
List every fail/unclear with the cheapest fix.
```

### R4 — 医学安全措辞猎杀

```text
ROUND R4 — MEDICAL-SAFETY WORDING HUNT

ROLE
You are a pharmaceutical regulatory reviewer and patient-safety editor. Context: the
dataset is a real child; the report will be published open (CC-BY) and read by the
family and patient communities. HARD RED LINE: nothing may read as clinical advice, a
treatment recommendation, or a suggestion to try / obtain / prioritize any drug.
Everything must remain a research hypothesis with testable predictions and stated
counter-evidence.

INPUT (attached)
report.md only.

TASK
1. Sweep EVERY sentence that names a drug (abstract, §2 table, §2.1–2.4, §3 predictions,
   §7). For each: could a lay reader (a parent of an affected child) take it as "we
   should try this"? Check: hedging present, hypothesis framing intact, counter-evidence
   attached, no dose/timing advice beyond cited dose references, no comparative
   "best/first choice" phrasing.
2. Sweep the abstract separately — it travels alone.
3. Check the predictions table (§3) reads as experiment design, not treatment protocol.
4. Reverse check: is any counter-evidence phrased so weakly that it functions as
   tokenism?

OUTPUT (中文)
For each finding: 原句 (verbatim) | 问题 | suggested rewrite (English).
End with an overall verdict: PASS or FAIL for the "no treatment recommendation" red
line, one-line justification.
```

### R5 — 红队评委（官方 Rubric）

```text
ROUND R5 — RED-TEAM JUDGE (official rubric)

ROLE
You are a skeptical hackathon judge. Other entries are strong; grade this one strictly,
as a judge, not a mentor. Do not reward effort — reward what is demonstrated on the page.

INPUT (attached)
report.md.

RUBRIC (official): Scientific Rigor 35 | Impact 25 | Innovation 25 | Scalability 15.

TASK (in this order; do not skip ahead)
1. Score each dimension (x/35, x/25, x/25, x/15) with a 2–3 sentence justification
   anchored to specific sections.
2. List EXACTLY FIVE weakest claims/sections, ranked. For each: (a) what a competing
   judge would write, in one sentence; (b) the cheapest fix that would move the score
   most.
3. Only after completing 1–2: up to three genuine strengths, one line each.
4. One sentence: is this report, as-is, shortlist-worthy in a competitive field?
   (yes / no / borderline + why)

OUTPUT in 中文.
```

## 4. 执行顺序与双模型选项

- 推荐序：**R4（5 分钟拿到红线结论）→ R1（挂后台慢慢跑）→ R2 → R3 → R5（收尾评分）**
- R1 如用 Deep Research 型服务，可将 A/B/C 三点任务整体下发，让它自主分配检索预算
- 双模型（如 Gemini + GPT）同协议各跑一遍：交集发现 = 必改；单侧发现 = 人工裁决
  后入发现表（处置写明「单侧发现，人工判…」）

## 5. 发现回收（三分诊，写入 `docs/cross-review-findings-2026-09.md`）

| 处置 | 判据 | 动作 |
|---|---|---|
| **修** | 事实错/超强度/红线措辞/表单缺口 | 直接改报告；若涉及台账更正：改 `research/evidence.jsonl` 对应条目 → **必须重跑** `python3 src/track2_repurposing/ledger.py lint` → 报告计数若变同步更新 |
| **缓** | 有效但属抛光/增强，非错误 | 记入 M5 抛光清单，终版提交窗口前统一处理 |
| **驳** | 审查者误读/超出证据支持的建议 | 书面记录驳回理由，**不静默丢弃**（评委若提同类质疑，驳回理由即应答预案） |

## 7. 自动化执行（runner）

`src/track2_repurposing/cross_review.py` = 本协议的 runner（零依赖，仅标准库）：

- **prompt 单一来源 = 本文档** §2 全局前缀 + §3 各轮 ```text 代码块——手改文档即生效，
  runner 不存副本（`check` 子命令校验解析完整性）
- 材料白名单硬编码于脚本 `ROUNDS`；`data/**` 路径一律拒绝（基因组红线双保险）
- 配置走 `.env`（已 gitignored；模板 `.env.example`）；`CROSS_REVIEW_TERMS_ACK=I_HAVE_VERIFIED`
  是红线 #3 的机器门——不确认条款不发包
- 命令：`check`（校验）/ `R4`（单轮）/ `all`（序 R4→R1→R2→R3→R5）/ 任意轮加 `--dry-run`
  （组装 prompt 落盘预览，不调 API 不记账）
- 原始输出 → `data/processed/cross_review/`（gitignored）；每次调用自动追加
  `docs/llm-usage.log` 一行；是否入账由人工分诊决定
- ⚠️ **R1 例外**：普通 chat API 无浏览能力，引文核验会大面积退化为 UNVERIFIABLE——
  R1 走带联网/Deep Research 类产品**手动执行**（§3 prompt 直接复制），runner 负责 R2–R5

## 8. 完成判据

五轮全部回收 + 每条发现都有处置 + 「修」类全部落地（含 lint 绿）+ llm-usage.log
补齐 → 交叉审核闭环，结论并入 M5 对抗审查门材料。
